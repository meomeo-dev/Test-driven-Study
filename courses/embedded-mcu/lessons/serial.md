# 串口通信与调试

本单元学习 UART 异步串行通信的基本原理与接线规范，掌握利用时间戳和节流技术
输出调试日志，设计按行分帧的命令解析协议，并实现非阻塞超时与有限重试的可靠
通信机制。

## 本单元知识点
- UART 帧与波特率：掌握起始位、数据位、停止位，波特率计算及交叉连线与共地要求。
- 串口日志与调试：掌握时间戳与状态打印，使用非阻塞节流与边沿触发避免串口拥塞。
- 命令协议与解析：掌握按行分帧流式接收、缓冲区边界防护及 ACK/ERR 回包确认。
- 通信超时与重试：掌握非阻塞超时计时、有限次数重试逻辑及进入故障保护状态。

## UART 帧与波特率
UART（通用异步收发器）是单片机与计算机或外部模块间最常用的全双工串行通信
接口。所谓“异步”，是指通信双方没有共享的时钟同步信号线，而是依靠双方预先
约定的相同波特率（Baud Rate，即每秒传输的二进制符号位数，单位为 bps）各自
维持独立的波特率发生器进行数据采样。

在最通用的 8-N-1 格式下，物理通信线路上平时保持高电平（逻辑 1 空闲态）。
每传输 1 个数据字节，必须在物理线路上依次打包包含 10 个二进制位：
1. 起始位（Start Bit）：固定为 1 位低电平（逻辑 0），提供下跳沿唤醒接收方；
2. 数据位（Data Bits）：固定为 8 位，且标准规定低位（LSB）在前、高位（MSB）在后；
3. 校验位（Parity Bit）：8-N-1 格式代表无校验位（None）；
4. 停止位（Stop Bit）：固定为 1 位高电平（逻辑 1），使总线恢复空闲电平。
因此，每传输 1 字节有效数据实际占用 10 位，有效数据传输率占总速率的 80%。

在硬件接线上，UART 通信必须严格满足“交叉互联”与“共地”两大核心原则：
- 发送端 TX 必须连接到对方接收端 RX，接收端 RX 必须连接到对方发送端 TX；
- 双方的 GND（地线）必须可靠直连，为双方提供相同的 0V 参考基准电平。
若未共地，因参考电平漂移会导致接收端将有效信号误判为噪声或乱码。

### 例题
在桌面分拣工位中，单片机需以 9600 bps 波特率、8-N-1 帧格式向上位机连续发送
36 字节的传感器状态包。请计算：
1. 传输该数据包在物理线路上传输的总二进制位数；
2. 不考虑字节间空闲时，发送完该数据包所需的理论通信时间（毫秒）。

【解答】
1. 在 8-N-1 格式中，每个字节需传输 1 位起始位 + 8 位数据位 + 1 位停止位 = 10 位。
36 字节的总二进制位数 = 36 × 10 = 360 位。
2. 在 9600 bps 波特率下，每秒传输 9600 位。
总传输时间 t = 360 / 9600 = 0.0375 秒 = 37.5 毫秒。

### 常见错误
1. 信号线同名直连：将单片机 TX 接到模块 TX、RX 接到 RX，导致双方输出冲突。
2. 忽略共地线：只连接 TX 和 RX 信号线而未接 GND，导致电平参考浮动出现大面积乱码。
3. 速率计算忽略帧开销：误按“波特率 ÷ 8”计算每秒字节数，遗漏了起始位与停止位。

## 串口日志与调试
嵌入式系统通常缺乏显示屏，串口打印是观察单片机内部运行逻辑与变量最直接的窗口。
在桌面分拣系统中，规范的日志应当包含“事件时间戳”与“当前状态”。
利用 millis() 函数获取自开机以来的毫秒数，格式化输出如 [1250ms] STATE: IDLE，
能够为定位偶发性延迟或状态机时序竞争提供量化依据。

在单片机编程中，必须严格防范“日志拥塞”。
UART 串口发送通常依赖硬件缓冲区（如常见的 64 字节环形缓冲区）。
若在无延时的 loop() 中高频持续调用 Serial.println()，缓冲区会在数毫秒内被填满。
缓冲区满后，后续的 print 函数将退化为阻塞等待，迫使 loop() 执行周期从几微秒
延长至数毫秒，极易导致分拣传感器漏检或舵机控制失步。

避免日志拥塞的两种核心手段是“状态转移触发”与“时间窗口节流”：
- 状态转移触发（边沿记录）：仅当状态发生变化（如 lastState != currentState）
  的瞬间打印一次流向记录（如 IDLE -> DETECTED）；
- 周期节流（Throttling）：对于必须持续监测的变量，利用非阻塞计时设定固定的
  更新间隔（如每 200 ms 打印一次），兼顾实时监控与系统响应速度。

### 例题
在分拣工位中，到位传感器持续检测工件时会频繁处于触发状态。请编写一段基于
millis() 的非阻塞节流代码，使得传感器在被遮挡期间每隔 500 ms 打印一次提示。

【解答】
```c
unsigned long lastLogTime = 0;
const unsigned long LOG_INTERVAL = 500;

void logSensorState(bool isBlocked) {
  unsigned long now = millis();
  if (isBlocked && (now - lastLogTime >= LOG_INTERVAL)) {
    lastLogTime = now;
    Serial.print("[");
    Serial.print(now);
    Serial.println("ms] Sensor: Workpiece Present");
  }
}
```

### 常见错误
1. 在无延时的 loop() 中无条件调用 Serial.print()，迅速耗尽缓冲区并拖慢系统。
2. 在中断服务程序（ISR）中调用 Serial.print()，因串口依赖中断导致死锁。
3. 使用 delay() 实现打印节流，导致单片机在延时期间无法检测输入信号。

## 命令协议与解析
UART 通信在物理层只保证单字节的收发，本质上是连续无界的流式数据（Stream）。
上位机发送的字符串在单片机端可能被拆成多个字节分散到达。
因此，必须在应用层制定数据帧协议。工业控制中最简便可靠的方案是“按行分帧”：
约定以换行符 \n（ASCII 码 0x0A）作为每条指令的结束标志。

单片机接收按行分帧命令的标准处理流程包括：
1. 轮询读取：当 Serial.available() > 0 时，逐字节调用 Serial.read()；
2. 缓存收集：非换行字符依次存入静态字符数组（接收缓冲区）；
3. 边界防溢出：每存入一个字符前，必须严格校验当前索引是否小于缓冲区最大下标，
   超长字符必须丢弃并报错，防止内存越界破坏其它变量；
4. 帧结束触发：读到 \n 时，在末尾写入 \0 封口形成 C 风格字符串，转入解析函数。

在交互设计上，必须建立“命令-回包确认（ACK/NACK）”闭环机制。
单片机成功解析并执行命令后，应向上位机回发确认（例如 OK:SORT_1\n）；
若命令未知或参数超出合法范围，则回发错误提示（例如 ERR:UNKNOWN_CMD\n）。
无回包的单向盲发极易因数据丢失导致上位机与下位机机械动作脱节。

### 例题
上位机向分拣站发送控制命令，格式为 S1\n（分拣至 1 号盒）或 S2\n（分拣至 2 号盒）。
请写出接收并解析该单字符参数命令的核心函数，在接收成功时回发 ACK，无效时回发 ERR。

【解答】
```c
void parseCommand(char *cmd) {
  if (cmd[0] == 'S' && (cmd[1] == '1' || cmd[1] == '2') && cmd[2] == '\0') {
    int bin = cmd[1] - '0';
    Serial.print("ACK:SORT_");
    Serial.println(bin);
  } else {
    Serial.println("ERR:BAD_CMD");
  }
}
```

### 常见错误
1. 误以为调用一次 Serial.read() 就能读出上位机发送的整句命令文本。
2. 写入缓冲区时未做长度限制检查，面对通信噪声或异常长串时引发缓冲区溢出崩溃。
3. 收到命令执行完成后不向上位机回发确认消息，导致上位机无法判断动作执行结果。

## 通信超时与重试
在工业分拣现场，由于振动、电磁干扰或上位机进程阻塞，发出的通信数据可能丢失。
若单片机采用 while (!Serial.available()); 死等上位机判定结果，
一旦通信中断，整个程序将永久卡死，造成工件堆积甚至机械碰撞。
因此，所有等待回包的逻辑都必须引入“通信超时（Timeout）”管理。

通信超时必须基于非阻塞计时实现：
在单片机发出质检请求（如 REQ:CHECK\n）的瞬间，记录发送时刻 sendTime = millis()，
并置位等待状态标志 waitingAck = true。
在主循环 loop() 中，定期评估 millis() - sendTime >= TIMEOUT_MS。
若在阈值时间内收到了应答，则清除等待标志并重置计时；
若超过阈值仍未收到回包，则触发一次超时事件。

面对偶发丢包，系统应提供有限次数的重试机会（例如允许重试 2 次）。
单片机在重试计数未超限时重新发送请求；若重试次数达到设定上限仍无响应，
必须立即停止重试并进入“故障安全（Fail-Safe）”状态：
1. 立即停止传送带电机并使分拣舵机归位至安全中立角度；
2. 开启声光报警灯，并锁存故障状态；
3. 退出正常分拣循环，等待人工现场复位排查。

### 例题
单片机向上位机请求视觉识别结果，单次超时设为 500 ms，最多允许重试 2 次（总计
最多发送 3 次请求）。若上位机故障始终无应答，计算从首次发送到最终判定故障停机
的总等待时间，并说明故障发生时系统的安全处置。

【解答】
1. 首次发送等待 500 ms 超时；第 1 次重发等待 500 ms 超时；第 2 次重发等待 500 ms
再次超时，重试计数达到最大限制 2 次。总等待时间 = 500 × 3 = 1500 毫秒（1.5 秒）。
2. 系统应立即进入 Fail-Safe 停机状态：切断进料动力、舵机置于中位、点亮故障红灯，
并通过串口发送一次 FATAL:COMM_TIMEOUT 报警。

### 常见错误
1. 使用阻塞式 delay() 或死循环等待回包，导致超时期间无法处理急停或到位信号。
2. 超时后无限制盲目重发，导致系统陷入无限死循环而无法及时停机报警。
3. 收到应答后忘记清零重试计数器和等待标志，导致后续命令交互立刻被误判为超时。

## 单元小结
- UART 通信采用异步传输，通信双方必须约定相同的波特率，且必须遵循交叉接线与共地原则。
- 串口日志能够提供时序与状态诊断，但必须通过边沿触发或非阻塞时间窗口节流防止发送拥塞。
- 面向无界字节流应采用换行符等协议边界按行分帧，并严格限制接收缓冲区大小防止内存溢出。
- 自动化控制系统必须建立 ACK/ERR 交互闭环，并在请求端建立非阻塞超时与有限重试的容错机制。
- 通信彻底失效时必须进入 Fail-Safe 安全状态，以硬件安全与流程受控为首要原则。
