# Question-chat dependency selection

Reviewed on 2026-11-08. Selected `@assistant-ui/react@0.15.33` with its
`LocalRuntime`, custom `ChatModelAdapter` and composable UI primitives.

## Project fit

The application uses React 19, TypeScript, Radix dialogs and a Go backend.
The existing Go LLM service owns Responses requests, OS credentials, explicit
proxy routing, model parameters and hosted government-domain web search.
The dependency needs to own conversation interaction without moving these
backend responsibilities.

The local `ai_agent_kms` SQLite knowledge base was queried read-only. Its
`ai_dependency_evaluations` table contains the independent Vercel AI SDK record
`dep_eval_l1_vercel_ai_sdk`, with a subjective score of 0.90 and the official
repository as source. Its `dep_all_frequencies` scan records `ai` in 48 sampled
repositories, `@ai-sdk/react` in 15 and `@assistant-ui/react` in five. assistant-ui
has no independent dependency evaluation. ChatScope was absent from the selected
packages, evaluations and scan records. These sample counts establish recorded
usage, with no inference about market share or production quality.

The isolated research agent first received public product names and generic
React/Go requirements. After finishing external research, the same agent performed
a separately requested local-only knowledge-base check without network access.
Local implementation details stayed in the main task. Current primary sources
establish the protocol and dependency costs used in this decision.

## Comparison

## Dependency boundary and verification

Only the React package is installed directly. Its transitive dependencies include
Radix UI, Zustand, Zod, assistant-stream, assistant-cloud and safe-content-frame.
The application configures LocalRuntime only. Hosted conversation storage and
cloud credentials are not configured.

The adapter consumes the application's NDJSON endpoint and yields complete
accumulated content snapshots. It maps verified government URLs to source parts
and forwards the runtime's abort signal to Fetch. The backend transport remains
independent of this dependency.

The exact package version and npm lockfile are committed. Installation reported
zero audit vulnerabilities. This is a point-in-time package audit, with upgrade
checks recorded in [the dependency inventory](../../dependencies.yaml).

Use stable public APIs. Review type checking, the production build and assistant
browser cases on upgrades. Replace the frontend runtime and primitives if API
churn, accessibility defects or measured bundle cost exceed their value.

The conversation runtime is loaded through a dynamic import on first activation.
The ordinary study entry includes the launcher and its project-owned styling.
The final build measured about 524 kB for the main JavaScript chunk and
701 kB for the conversation chunk, or about 162/207 kB gzipped. Vite retains its
500 kB chunk-size advisory. The generated transparent avatar is about 1.15 MB.

The follow-up requirement adds arbitrary window placement and independent width/
height resizing. The existing non-modal Radix dialog supplies the floating shell;
native pointer capture and small geometry functions own positioning, bounds and
local preferences. No additional drag/resize dependency is required. assistant-ui
continues to own the conversation runtime and message/composer primitives.

## Markdown rendering

The selected renderer is `@assistant-ui/react-markdown@0.14.25` with
`remark-gfm@4.0.1`. Both use MIT licenses. The adapter's declared
`@assistant-ui/react ^0.15.0` peer range matches the existing 0.15.33 runtime,
and its React peer supports 18 and 19. The adapter reads the current message
part directly, so the server transcript and NDJSON transport stay intact.

The isolated research agent checked current official documentation and published
package declarations, then separately inspected the explicitly authorized local
knowledge base without network access. Its `dep_all_frequencies` records were
reconciled against per-repository dependency inventories and the original scan.

| Candidate | Local sampled repositories | Integration assessment |
| --- | ---: | --- |
| react-markdown | 107 | CommonMark renderer and the selected adapter's underlying parser; direct use is the replacement path. |
| remark-gfm | 103 | Adds GFM tables, deletion, task-list and autolink syntax; selected. |
| @assistant-ui/react-markdown | 2 | Direct assistant text-part integration; selected. |
| streamdown | 25 | Adds unfinished-syntax repair and block caching; reconsider if those become acceptance requirements. |
| markdown-it | 25 | HTML-string output would require an additional React rendering boundary. |

These are package-name occurrences in a 2,849-repository sample. The knowledge
base contains no independent dependency evaluation for these five candidates.
The counts do not establish performance, security, quality or overall market
adoption. The choice rests on the current APIs and the project's existing runtime.

Only assistant text uses Markdown. User messages retain their plain-text renderer.
GFM is enabled through an explicit remark plugin. The renderer drops raw HTML
and image elements, retains the underlying default URL filtering, and makes only
HTTP(S) links clickable. Links open with `noopener noreferrer`. Existing verified
source parts remain separately visible. Tables and code scroll within the window.

Rendering is deferred during rapid updates with artificial text animation
disabled. The original model text is retained. Incomplete emphasis or links can
remain text until their delimiters arrive. The chosen parser does not claim
automatic repair of every unfinished Markdown construct.

The install audit reported zero vulnerabilities. The installation added 101
parser/adapter packages to the existing lockfile. The parsing chain is mainly
react-markdown, unified, remark and micromark, plus GFM extensions. The boundary
is the single assistant Text component, which can be replaced independently.
