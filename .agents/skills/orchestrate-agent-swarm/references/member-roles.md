# 成员角色规则（Member Roles）

执行到工作流第 1、3、4、6、7、8 步时加载：拆分与配置成员、写派发书与计划文件、处理回报、
组织核对、收尾。成员（worker、verifier、monitor）也按派发书的指示读取本页自己的一节。

## 1. coordinator（主会话）

**只派发、验收与汇总，不做工作。**

- 调查、实现、测试、核对都派给成员。
- 能做的：
  - 为了回答用户而做的只读快速查阅；
  - 拆分前为划定所有权做的只读摸底：目录结构、入口文件、相关测试与构建命令、项目规则，够
    划定所有权即止，不改文件，不跑构建；
  - 阅读成员的产出并作判断，包括打开页面或运行产物抽查结果；
  - 提交前运行项目规定的提交门禁（如 `pnpm verify`）。它属于按项目规则提交，不另派成员。
- 逐条对照验收口径的核对与完整测试派给 verifier。
- 每一轮都保持简短：处理完一条回报就结束这一轮，不在自己的长任务里让用户和成员等。

**拆分与规模：**

- 按文件、目录或问题划分，每块只有一个所有者。两个成员写同一个文件是要在设计时消除的
  失败模式，不是运行中再协调的事。
- `owns` 写成员要改的文件或目录：成片改一个目录时写目录，散在几处时逐个写文件。它决定
  活动判定扫描哪里，也是所有权的登记；不限制成员读别处。
- 运行中调整负责范围用 `assign`：成员合理拆出了派发书没列的文件时，把新文件登记到它名下；
  作者已结束而修正落在它的文件上时，把文件转给待命中的作者，再发 `fix`。只转交已完成或
  待命中的成员的路径，运行中的成员先等它发 `done`。`assign` 发出的 `note` 不唤醒待命成员。
  2026-11-19 的一次真实项目运行中，这两种情况都出现过，转交只能写在消息正文里，名单的
  `owns` 无法同步。
- worker 数等于能真正独立推进的块数；每 2 到 4 个作者配 1 个 verifier；每期配 1 个 monitor。
- 同构的分片（例如按目录分的多个 reviewer）用 `add --count` 批量登记成一个组。两个以上
  互不相干的工作区，各建一个组（`add --group`），区内消息发给组。
- 并行上限取用户或项目规则（没有规则时为 3），monitor 与待命成员都计入上限。超过上限的
  成员排进后续各期。前一期有成员结束时，立即把空出的位置交给下一期中不依赖它的成员。
- 给 verifier 留位：作者都完成后，只让修正最可能落到的作者待命，给其余作者发 `stop`，再派
  verifier。上限为 3 时的排法：monitor 加两名作者；派 verifier 前停掉其中一名，停掉的作者的
  文件需要修正时用 `assign` 转给仍在待命的作者。2026-11-19 的一次真实项目运行中，两名作者
  待命加 monitor 占满 3 个位，两期都要先停一名作者才派得出 verifier。
- 只登记本批能启动的成员：登记即派发，未启动的成员 12 分钟后会被判 `stalled`。2026-11-19
  的自举审查中，`add --count 3` 遇到并行上限 3（含 monitor），第 3 名只能改为空位出现时
  补登。
- 成员数宁少勿多：每个成员都要花 token，即使它在等待。

**组的调整：**

- 工作区中途增减成员用 `group --join`、`group --leave`。新加入的成员要补读区内历史或开始
  新工作时，另发 `brief` 指向派发书的相应一节：`group` 发出的 `note` 不唤醒待命成员。
- `group` 发出的 `note` 是名单变更通知，不核销成员的待答复：调整组不影响回报的处理。
- `plan.json` 引用该组时，调整后重写计划：组被清空后，`overview` 因计划校验失败退出 1。
- 区结束时，先给组内没有其他工作的成员发 `stop`（都没有时可以发给整个组），再
  `group --archive`：归档后不能再发给该组，也不能再加人，历史仍可用 `read --group` 读取。
  成员同时属于其他组时，发给组的 `stop` 也会结束它在别处的工作。
- 命令与条件见 `references/board-protocol.md` 第 4 节。

**待命：**

- 预计会有后续任务（下一阶段、修正）的成员，在派发书里写明完成后待命多少分钟。审查类
  任务的作者默认待命：verifier 之后几乎总有修正项。
- 待命成员点名即醒，保留原来的上下文，比续接已结束的成员便宜得多。
- 待命成员占并行位：上限紧张时少开待命；用不上时尽早发 `stop`。

**派发书（`briefs.md`）：**

- 公开：所有成员都能读到别人的派发书。不写不该让整个 swarm 知道的内容。
- 派发书是成员拿到的全部上下文。成员没有看过对话，也没读过 coordinator 读过的文件。
- 每节写明：
  - 负责什么，不得触碰什么；
  - 输入在哪里，要回答哪些问题；
  - 产出文件清单，即完成判据；
  - 本项目的写作规范、禁读路径与环境注意事项。
- 环境注意事项包括正在运行、会监视文件变化的开发进程（用 `ps` 查看，如 dev server、
  `tauri dev`）：写明改到哪些路径会触发重建或重启。2026-11-19 的一次真实项目运行中，成员改了
  `src-tauri` 下的一行注释，用户正在用的开发客户端随之重建并重启。
- 通用规则写明成员不执行 git 写操作（含 `git add`、`git rm`、`git mv`），删除或移动文件
  直接用文件操作。同一次运行中，成员用 `git rm` 删文件，删除进了暂存区。
- 允许成员之间直接交接时，写明谁可以交给谁、交接什么（`handoff` 或 verifier 的 `fix`）。
  没写的交接一律经 coordinator。
- 后续成员需要前一期的产出时，按路径与小节引用，不转述内容。

**验收口径（`acceptance.md`）：**

- 照录用户或 spec 的原话，coordinator 不改写。
- coordinator 从项目规则或代码约束补充的技术口径（最小窗口尺寸、兼容范围、性能下限等），
  在同一文件另起一节「补充口径（coordinator）」，逐条写来源，verifier 一并核对。2026-11-19 的
  一次真实项目运行中，用户原话没有提窗口下限，verifier 只核对了两种常用宽度；coordinator 在
  客户端最小窗口下才发现横向溢出，补发了修正。
- verifier 依据它核对，不依据派发书核对。用户历史中出现过这种情况：verifier 与派发书出自
  同一个人，放行之后用户仍连续发现遗漏。

**计划文件与总览：**

- 登记本期成员之后写 `<run-dir>/plan.json`：目标一句话，各工作线对应派发书的各节。改派、
  调整分工或登记下一期之后重写。格式见 `references/overview-and-plan.md` 第 1 节。
- monitor 每次巡检把总览写到 `<monitor 的 owns>/overview.md`。向用户汇报进度时引用它，或
  运行一次 `overview` 打印。

**接收回报：**

- 宿主有事件监视时，在登记第一批成员之后、启动它们之前挂上 `watch --for coordinator`。
  成员的 `done`、`blocked` 与 monitor 的 `stall` 会逐条推给主会话。成员之间的 `handoff`
  不推送，抄送 coordinator 也只留记录。
- `watch` 默认从 coordinator 最后一次发言之后开始，挂上之前到达、还没处理的消息也会输出。
- `watch` 到时，最后一行给出 `--since <seq>`，带上它重新挂上，中间的消息不会漏。
- 成员结束运行时，宿主也会通知主会话。两种通知按同一流程处理。

**处理回报：**

1. 每收到一条通知，先运行 `status`，按“待处理事项”（`attention`）逐项处理，再读相关的
   `done` 消息与产出。每项的 `action` 是处理建议，`refs` 是要看的消息。
2. 逐份判断，并在板上给发件人回一条消息——只有发给该成员（直接、经组或 `all`）的消息才
   核销它的待答复，`group` 与 `assign` 发出的名单变更 `note` 除外：
   - 接受：发 `accept`；
   - 退回：发 `fix`，正文写修正项的位置；
   - 追加任务：发 `brief`，正文指向派发书里新增的一节；
   - 移交：把空出的位置交给下一个成员。
3. 送达：
   - `status` 显示 `reachable` 的成员在待命中，板上的消息会直接唤醒它。
   - 运行中的成员在下一次发 `progress` 或 `done` 前读到发给它的消息。
   - 已结束的成员看不到之后的消息。发出 `fix`、`brief` 或 `resume` 后，必须用宿主的续接
     手段把同样的内容送达给它，或者改派新成员 `<name>-2`，并在派发书里引用原作者的产出。
   - 成员读到并开始处理时会发 `start`。发出后超过阈值仍没有 `start`，`status` 给该成员
     标 `needs-resume`：按上一条送达。成员之间的 `handoff` 没有被读到时也一样。
4. 一个作者的多条修正项合成一条消息。续接会重新载入该成员的整段会话：2026-11-19 的实操
   中，每次续接约 13 万到 21 万 tokens，而每次只改了 2 到 10 处。
5. 待命成员没有后续任务时，发 `stop`（可以发给整个组），腾出并行位。
6. monitor 报 `stall` 时，在这一轮内处理正文列出的各项，再给该 monitor 发一条 `note`
   写明处理结果，核销这条报警。`watch` 模式下 monitor 继续巡检，不派继任；同一事项还没
   解决时，它会按限频规则再报。
7. monitor 发 `done` 结束运行（正文注明“巡检到上限”“休眠到期”，或 `exit` 模式报警后）时，
   同样给它发 `note` 核销；swarm 未收尾时派下一任 `monitor-N`。收尾时写完核对结果的
   `done` 见下文“收尾”。
8. monitor 休眠时发的是 `note`（正文“休眠”），不需要答复。休眠中的 monitor 仍是 `active`，
   任何新消息都会让它回到巡检。

**运行中追加要求：**

1. 把用户的新原话追加到 `acceptance.md` 的新一节，注明日期，原有各节不改。
2. 在 `briefs.md` 加下一期的各节，写明改动范围与产出。
3. 能由待命中的作者接手的，用 `assign` 调整它的 `owns` 与 `output`，再发 `brief` 指向新的
   一节；否则登记新成员。
4. 重写 `plan.json`；新一期完成后再派 verifier，按追加后的 `acceptance.md` 核对。

**替换与放弃：**

- 正常收尾用 `stop`：worker 与 verifier 收到后直接结束运行，不再发言，`status` 的
  `stopped=#<seq>` 与总览状态列的“已停止 #<seq>”标出它们；运行中的成员读到 `stop` 时先发
  `done` 或 `blocked`。monitor 写完核对结果再发 `done`。
- `remove` 只用于放弃一个成员：之后它的任何发言都会被拒绝。
- 替换成员时先 `remove` 原成员，再登记 `<name>-2`，派发书引用原成员的产出。

**会话重启或上下文压缩后的恢复：**

1. 运行 `status`：`attention` 列出全部待处理事项；`unanswered` 是还没答复的回报，各成员的
   `pending` 与 `needs-resume` 是还没送达的消息，`reachable` 是可以直接点名的待命成员。
2. 不带 `--since` 重新挂上 `watch --for coordinator`：它从 coordinator 最后一次发言之后
   开始，补上期间到达的消息。
3. 续接所需的子代理 ID 只在会话里。ID 已丢失的成员改派 `<name>-2`，派发书引用原产出。

**收尾：**

1. 抽查 verifier 提出的修正是否已落到文件。monitor 只核对时间与行数，不核对内容。
2. 向仍在待命或运行的成员、以及 monitor 发 `stop`（可以发给组；已归档的组逐个点名）。
   休眠中的 monitor 也会被它唤醒。
3. 等 monitor 写完核对结果并发 `done`（`watch` 会推送）。
4. 发 `done --to all`。
5. 停掉 `watch`，导出 `board.md`，用 `overview --out <run-dir>/overview.md` 导出总览，删除
   临时文件。
6. 向用户汇报结论、材料位置和未验证项。
7. 按项目规则提交：提交前运行项目规定的提交门禁。运行目录不在 `.gitignore` 里时，不随功能
   改动提交，向用户说明位置并询问是否入库。2026-11-19 的一次真实项目运行中，默认运行目录落在
   项目已入库的 `.agents/` 下。

## 2. worker

`START` 是你最近一次发出的 `start` 的序号（`post` 的输出以 `#<seq>` 开头）。

1. 读 `briefs.md` 的通用规则和自己的一节，然后发 `start`，记下 `START`。
2. 只写自己 `owns` 下的路径。不改别人的文件；派发书没写的写操作一律不做，含 git 的提交、
   `git add`、`git rm` 与 `git mv`；删除或移动文件直接用文件操作。
3. 每完成一个产出文件发一条 `progress`。全部完成后发 `done`，正文列出产出文件和三行以内
   的结论。
4. 每次发 `progress` 与 `done` 之前，先读一次板：
   `read --for <你的名字> --since START --tags brief,fix,resume,handoff,stop`。
   - 有 `brief`、`fix`、`resume`、`handoff`：发 `start`（正文写“开始处理 #<seq>”），更新
     `START`，把它并入当前工作。
   - 有 `stop`：尽快收尾，发 `done` 或 `blocked` 后结束运行。
5. 做不下去时发 `blocked` 写明原因，然后结束运行。不要静默停下。
6. 被唤醒或被续接修正时：先发 `start`，更新 `START`，再逐条回到证据核实再改。不同意某条
   时不改，用一行 `note` 说明理由。最后发 `done`，正文写“修正完成：<逐条一句>”。
   CLI 要求先 `start` 后 `done`：`start` 是“已读到修正项”的唯一凭据。还有待处理消息时
   CLI 也拒绝 `done`，并列出这些 `#seq`：照第 4 条先处理。收到的 `handoff` 同样处理。
7. 派发书要求待命时，发完 `done` 不立即结束，进入待命循环：
   1. 发 `post --tag standby --minutes <N>`，正文写“待命”（`standby` 是标签，不是子命令）。
      输出里“至”后面的时间是截止时间 `UNTIL`。
   2. 运行 `wait --for <你的名字> --since START --tags brief,fix,resume,handoff,stop
      --until UNTIL --timeout-seconds 590`。`--tags` 让 `accept`、`note` 之类的告知不再
      唤醒你。
   3. 返回的消息里有 `stop`：结束运行，不再发消息。
   4. 返回的消息里有 `brief`、`fix`、`resume`、`handoff`：按第 6 条处理（新任务就读派发书
      里指向的一节），完成后发 `done`，回到第 1 步重新待命。
   5. 返回 `timed_out`：`deadline_reached` 为真（文本输出“已到截止时间”）就结束运行，
      否则回到第 2 步。
8. 派发书允许直接交接时，把写明的下一步工作直接交给写明的同伴：
   - 命令：`post --from <你的名字> --to <同伴或组>,coordinator --tag handoff --text "<对方
     要做什么；依据的 #seq 或文件>"`。抄送 coordinator 让它在读板时看到这次交接。
   - `--to` 须点名成员或组，不能是 `all`，也不能只有 coordinator；你的状态须为 `active`
     或 `done`（待命中也可以发）。
   - 发之前用 `status` 看对方：运行中或 `reachable` 时它能读到；已结束的成员读不到，改为在
     `done` 或 `note` 里告诉 coordinator 由它续接。
   - 交接不改变你自己的完成判据：产出照常 `progress`、`done`。
9. 最终回复写：产出文件清单、每个文件一句话摘要、对 coordinator 的决定最关键的事实及其
   证据位置。

## 3. verifier

- 只报告，不修改作者的文件。verifier 自己动手修，就等于两个人写同一个文件。
- 依据 `acceptance.md` 与作者标注的来源逐条核对。每个作者至少抽查 8 条关键结论；对最终
  决定有影响的结论全部核对。
- 每条写：结论、来源、核对结果（确认 / 错误 / 无法核对）、修正建议（文件:行）。
- 另列跨文档的矛盾，以及对项目规则（版权、保密、篇幅）的违反。
- 产出写在自己的 `owns` 下，发 `done` 时列出错误数与最重要的问题。
- 派发书允许直接交接、且作者在待命中（`status` 显示 `reachable`）时，可以把该作者的修正项
  合成一条 `fix` 直接发给作者，并抄送 coordinator（`--to <作者>,coordinator`）。作者改完后，
  最终验收仍由 coordinator 负责。
- 待命、读板、修正与 `handoff` 的规则同 worker 第 4、6、7、8 条。派发书写了待命分钟数时，
  发完 `done` 照第 7 条待命：coordinator 要你复核修正时会点名。2026-11-19 的一次真实
  项目运行中，verifier 的提示词模板没有待命一段，它发完 `done` 就结束了。

## 4. monitor

monitor 是停滞监视者：不做研究，不评审内容，不修改成员文件；只写自己的 `owns`。它发现
“所有人都在等别人”的状态，报给唯一能推动它的 coordinator，并每次巡检写一份总览。

**唤醒方式**由派发书与提示词的 `{{wake_by}}` 指明：

- `watch`：宿主有事件监视（Claude Code 的 `Monitor`），`stall` 经 coordinator 的 `watch`
  推给它。monitor 报警后继续巡检。这是 Claude Code 下的默认。
- `exit`：宿主没有事件监视。monitor 报警后发 `done` 并结束运行，靠宿主的结束通知唤醒
  coordinator。

**巡检循环**（`LAST` 是已读到的最高序号）：

1. 开始时运行 `status --json`，取 `head_seq` 作为 `LAST`，发 `start`。
2. 运行 `wait --since LAST --for <自己的名字> --timeout-seconds 180`。它就是巡检节拍：
   有发给自己的消息时提前返回，否则 3 分钟后返回。
3. 巡检，依次：
   1. 运行 `status --json`，更新 `LAST`。
   2. 运行 `overview --dir <run-dir> --out <owns>/overview.md`。它失败时（如 `plan.json`
      校验失败）把错误写进本次的巡检记录，照常判断。
   3. 向 `<owns>/ticks-<name>.md` 追加一行巡检记录，格式见下文。
4. 按下列顺序判断：
   - swarm 状态为 `finished`，或收到发给自己的 `stop`：执行第 6 步，结束。
   - 报警：按下文“报警与限频”。`exit` 模式下报警后发 `done` 并结束运行。
   - 休眠：满足下文“休眠”的条件时进入休眠。
   - 其他情况：回到第 2 步。
5. 一次运行最多 20 次巡检，休眠期间不计。到上限时执行第 6 步，`done` 正文注明“巡检到
   上限”，结束。
6. 收尾：逐个核对本期成员的 `outputs` 是否存在、非空，结果写入 `<owns>/check-<name>.md`，
   再发 `@coordinator [done]`。

**巡检记录：** 每次巡检一行，写时间、swarm 状态、板头序号（`head=`）、`attention` 的 id
列表、本次报警的 id 与 refs（`alarm=<id>(#refs)`，没有报警时写 `-`）。发出 `stall` 后另追加
一行 `stall #<序号>`；休眠中每次等待超时另追加一行“休眠”：

```text
- 2026-11-19T08:12:03-05:00 attention head=#21 ids=shard-2:needs-resume,coordinator:unanswered alarm=shard-2:needs-resume(#16)
- 2026-11-19T08:12:04-05:00 stall #22
- 2026-11-19T08:40:05-05:00 休眠
```

限频、休眠与 20 次上限的判断只依据这个文件：上下文压缩后，从它恢复每个 id 的报警次数、
上次报警的巡检与 refs、自己发出的 `stall` 序号、板头序号连续不变的次数，以及本次休眠已
超时的次数。`stall` 行与“休眠”行不计入巡检次数。

**归因：** `attention` 每项的 `subject`（停在谁身上）、`refs`（哪些消息）与 `action`（该做
什么）就是停滞的归因，对应 agy monitor 的停滞归因。报警正文照写这几项，不另作推断。

**报警与限频：**

- 同一 id 在连续两次巡检中都出现，才报警。
- 已报过的 id，只有 refs 变化，或距它上次报警已过 3 次巡检，才再报；同一 id 最多报 3 次。
- 记录与比较 refs 时，去掉自己发出的 `stall` 的序号：这些报警本身计入
  `coordinator:unanswered`，不去掉就会每次都算变化，间隔规则失效。
- 一次巡检最多发一条 `@coordinator [stall]`，正文逐项写 id、refs、since 与 action。

**休眠：**

1. 条件：`attention` 非空，其中每个 id 都已至少报过一次，且自最近一次报警起板头序号连续
   3 次巡检不变（coordinator 已被告知而没有动作）。`attention` 为空时不休眠：成员都在干活
   时照常巡检；无人干活时等 `coordinator:idle` 出现并报过一次，再按本条休眠。
   报警与休眠在同一次巡检都成立时先报警（第 4 步的顺序）。refs 不变时，同一 id 每隔 3 次
   巡检再报一次，所以休眠发生在它报满 3 次、之后板头又连续 3 次巡检不变时。2026-11-19 的
   前向验证中，monitor 依次报了 3 次，第 3 次之后的第 3 次巡检进入休眠。
2. 发 `@coordinator [note]`，正文写“休眠”；`LAST` 取这条 `note` 的序号。不用 `done` 加
   `standby` 表示休眠：`done` 需要 coordinator 答复，而答复本身又会唤醒 monitor。
3. 运行 `wait --since LAST --timeout-seconds 590`，不带 `--for`：任何新消息都返回。
4. 超时返回：向巡检记录追加一行“休眠”。`owns` 的修改时间因此保持更新，休眠中的 monitor
   不会被判停滞。本次休眠的“休眠”行满 12 行（约 120 分钟）即休眠到期：执行第 6 步，
   `done` 正文写“休眠到期”，结束。否则回到第 3 步。
5. 有新消息：立即回到巡检循环第 3 步，不先等一个节拍，也不发 `start`：monitor 在休眠中
   一直是 `active`。

规则：

- 只依据 `status` 的 `attention`，不自己计算时长，不凭板上的自由文本判断。事项已按阈值
  （默认 12 分钟）过滤：swarm 无人干活且超过阈值没有新消息时，才有 `coordinator:idle`。
  2026-11-19 的自举审查中，monitor 按“`unanswered` 非空连续两次”报警，coordinator 正常
  处理回报约 3 分钟就被报 `stall`。
- 报警后继续巡检（`watch` 模式）。同一次审查中，monitor 报一次 `stall` 就结束运行，之后
  无人监视。
- 只发给 coordinator，不发给 `all`，也不直接点名成员：待命成员只被发给它的行动消息唤醒，
  monitor 不能发这些标签；已结束的成员读不到任何消息。点名都无作用，由 coordinator 续接或
  改派。
- 待命成员的状态是 `done`，不算停滞。
- 巡检辅助脚本写系统临时目录。2026-11-19 的实操中，monitor 在自己的目录里留下过隐藏
  脚本。
